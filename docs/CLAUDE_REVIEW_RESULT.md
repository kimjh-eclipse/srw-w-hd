# Claude 검토 결과 (2026-11-11)

`CLAUDE_REVIEW_HANDOFF.md`에 대한 답변이다. 주체: Claude(정적 분석·검사 도구·공통 수정). 실제 게임 화면 확인은 하지 않았다.

## 1. 접근 방식의 결함

1. **검사가 플레이어와 다른 코드 경로를 돈다.** `verify_foreground_scenes.py`는 `HDRenderer()`를 동기 준비로 만들고 `paused=True`로 한 프레임만 그린다. 이 경우 코어는 `SRWWAsyncParts=false`라 연결된 파츠를 전부 즉시 숨기고, 렌더러는 텍스처를 그 자리에서 만든다. 실제 플레이어는 비동기 준비 + 런타임 타일 조립 + 지연된 ready 핸드셰이크 + 연속 재생이다. 로딩 지연, 원본 잔류, 소실은 이 검사에서 구조적으로 나타날 수 없다.
2. **검사가 결과가 아니라 산출 여부를 본다.** 배열 크기만 단언한다. `scripts/verify`에 검사 스크립트가 90개 가까이 있지만 "화면에 무엇이 HD로 나왔는가"를 재는 것은 없었다.
3. **숨김과 그리기가 원자적이지 않다.** 코어는 프레임을 에뮬레이션할 때 가진 ready 집합으로 네이티브 OBJ/BG 타일을 숨기고, 렌더러는 나중에 다른 프로세스에서 자기 캐시 상태로 그릴지 정한다. 그 사이 `begin_stage()`의 캐시 비움이나 StageCache 용량 축출이 일어나면 네이티브도 HD도 없는 프레임이 나온다.
4. **파츠 단위 대체를 기체 단위 완성으로 셌다.** 대체는 OAM 파츠 하나씩 결정된다. 한 기체의 일부 파츠만 연결되면 HD 몸통에 원본 날개가 붙는다. 등록 수·타일 일치 수는 이 혼재를 드러내지 못한다.
5. **공통 원인 전에 개별 자산을 쌓았다.** 3·4번은 모든 기체에 공통인데, 장면별 자산 연결과 예외 조건(`cyan` 감지, `restore_rect`, `repeat_native_plane` 등)이 먼저 늘었다.

## 2. 적용한 변경

- `emulator/hd_parts.py`
  - `PartsRenderer.rescue()` 추가. 코어가 이미 숨긴 파츠(제어값 bit31 꺼짐)의 텍스처가 렌더러에 없으면 그 자리에서 준비한다. 디스크 캐시 적중이 일반적이고, 런타임 조립 텍스처는 작업 프로세스를 최대 0.5초 기다린다.
  - `compose()`가 `last_stats`에 결과 계수(drawn / waiting / vanished / occluded / rescued, 네이티브 픽셀 면적 포함)를 남긴다. 그리기 동작은 바꾸지 않는다.
- `scripts/verify/verify_runtime_path.py` 신규. 저장 상태를 실제 실행 경로(비동기, 런타임 조립, ready 지연 `--lag`, 60fps 연속 재생)로 돌리고 장면마다 판정한다.
  - `FAIL`: 소실 프레임이 있음
  - `INCOMPLETE`: 로딩이 가라앉은 뒤에도 HD 면적 비율이 98% 미만
  - `REVIEW`: 이 도구가 잴 수 있는 결함 없음. 사람이 저장된 그림을 봐야 함
  - "verified"라는 판정은 없다.
  - 그림의 왼쪽은 코어 출력(ready 파츠가 이미 숨겨진 상태), 오른쪽은 HD 합성이다.

## 4. 확인하지 못한 것

- 사용자 제보의 FMP 기체 소실이 3번 경로인지는 모른다. 기본 30장면의 정상 재생에서는 소실이 0이었고, 강제 비움으로만 재현했다. 제보 화면(어두운 구름 배경 + 붉은 효과, 기체 없음)은 컷인 168 순서 문제일 수도 있다. 그 장면의 저장 상태로 이 검사를 돌려야 가려진다.
- 그레이트 마징가 보조창, 썬더 브레이크 파츠 깨짐, 대사창 침범은 건드리지 않았다. 이 검사는 잘못된 그림이 연결된 경우(HD로 그려졌지만 틀림)를 잡지 못한다.
- 수정은 새로 시작한 프로세스에만 적용된다. 실행 중인 테스트 창에는 반영되지 않았다. 배포물(`dist/`)도 그대로다.
- 커밋하지 않았다.

## 5. 다음 순서 제안

1. 제보 장면 6개를 저장 상태로 고정하고 `--state`로 돌려 FAIL/INCOMPLETE를 먼저 숫자로 확보한다.
2. 혼재 정책을 코어에서 정한다. `SRWWHD_ShouldSkipRobot`의 프레임 선행 루프에서 OBJ 팔레트 슬롯별로 연결·미연결 면적을 세고, 미연결 비중이 큰 슬롯은 그 프레임에 전부 네이티브로 둔다. 효과가 기체와 팔레트를 공유하면 깜빡일 수 있으므로 임계값은 이 검사의 `mixed_frames`로 조정한다. DLL 재빌드가 필요해 이번에는 적용하지 않았다.
3. `SRWWIndexedBindings`는 팔레트를 뺀 인덱스 해시만으로 연결하고 먼저 등록된 것이 이긴다. 작은 파츠의 오연결 후보이므로 16×16 이하 파츠의 충돌 수를 먼저 집계한다.
4. 완료 기준은 "해당 무장의 전 구간 재생에서 FAIL 0, HD 면적 비율 98% 이상, 그리고 저장된 그림을 사람이 확인"으로 둔다.

## 6. 2차 작업 (같은 날, 사용자 지시로 직접 적용)

- **기체 단위 원본 유지** (`emulator/desmume/desmume/src/srww_parts_impl.h`): 전투 화면 배치일 때 OBJ 팔레트 슬롯별로 HD 면적과 원본 면적(미연결 + 로딩 중)을 세고, 원본 비중이 10% 이상이면 그 프레임에 슬롯 전체를 원본으로 둔다. 텍스처 로딩은 계속된다. 환경 변수 `SRWW_UNIT_FALLBACK_PERCENT`로 바꿀 수 있고 0이면 끈다.
- 숨김 판정을 제어값 bit31 하나로 통일했다. 코어와 렌더러가 같은 프레임 결정을 본다.
- 임계값 비교(11장면): 고라이온 혼재 프레임 86 → 6, unit 214 HD 깜빡임 69회 → 1회(10%), 39회(25%). 10%를 기본값으로 했다.
- 코어 설치: `desmume_libretro.dll`을 새 빌드로 바꿨다. 이전 빌드는 `desmume_libretro.previous.dll`이다. `emulator/hd_core.patch`를 다시 내보냈다.
- 전체 재생(저장 상태 161개, 150프레임): **FAIL 0, INCOMPLETE 102, REVIEW 38, NO_HD_PARTS 21.** 기록은 `test_current/combat/runtime_path/regression/report.json`.
- 미연결 OBJ 파츠 650종과 런타임 조립 실패 293종을 `gaps.json`·`gaps.png`로 뽑았다. 그림 작업 지시는 `docs/IMAGE_REWORK_FOR_CODEX.md`.

여전히 확인하지 못한 것: 실제 게임 화면 확인, 제보된 FMP 소실의 원인, 보조창 그림, 틀린 그림이 연결된 경우, 대사창 침범, 배포물(`dist/`) 재빌드, 커밋. 핸드오프 문서는 unit 297을 FDS 겟타로 적었지만 이름 목록에는 마징카이저KS로 나온다. 장면과 기체 ID 대응을 다시 확인해야 한다.

## 7. 3차 작업: 로딩 (2026-11-12)

### 원인 (측정)

- 파츠 하나의 첫 가공(자르기·리샘플링·정렬 탐색)이 중앙값 77ms, 최대 274ms였고, 작업 프로세스 하나가 한 줄로 처리했다.
- 굽기 전 저장소에는 48,561행이 있었지만 현재 키로 유효한 것은 89,199개 중 36,191개였다. 키에 아틀라스 수정 시각과 정렬 코드 해시가 들어가므로 그림이나 코드를 고치면 무효가 된다.
- 캐시에 있는 파츠도 읽기 0.56ms에 팔레트 변환표 계산 약 20ms가 붙어 20.5ms가 걸렸다.
- 텍스처 작업 프로세스는 시작에 3.3~4.0초가 걸린다.

### 적용

- `scripts/assets/bake_parts.py`: 전체 소스 파츠를 미리 가공해 `graphics/parts_baked.sqlite`에 저장. 4배, WebP 무손실. 89,199개, 오류 0, 1.28GB (이전 8배 zlib 저장소는 8.4GB이고 지우지 않았다).
- 렌더러가 구운 파츠를 처음부터 준비됨으로 알리고, 그릴 때 저장소에서 직접 읽는다.
- 팔레트 변환표 755종을 `graphics/palette_luts.npz`(1.6MB)로 미리 계산. 캐시된 파츠 읽기 전체가 20.5ms → 0.44ms. 미리 계산한 표가 실행 중 계산한 것과 같은지 표본 1개로 확인했다.
- 런타임 조립 실패를 저장소의 `assembly_misses` 테이블에 기록해 다음 실행부터 재시도하지 않는다(현재 320건). 타일 자료나 조립 코드가 바뀌면 기록이 무효가 된다.
- 구운 파츠를 메모리에 미리 올릴 때 준비 목록 전체(9만여 개)를 코어에 다시 보내던 부작용을 없앴다. 첫 굽기 직후 검사에서 일부 장면이 느려진 원인 중 하나였다.
- 검사기가 원본 표시를 `loading`(그림은 있는데 준비 안 됨)과 `held`(준비됐지만 10% 규칙으로 원본 유지)로 나눠 잰다. 상태를 불러온 직후 5프레임은 코어가 준비 목록을 받기 전이라 `loading` 집계에서 뺀다.

### 화질

8배에서 3.75배로 줄인 것과 4배 저장본에서 줄인 것을 표본 300개로 비교했다. 평균 차이 0.25/255, 최악 22/255. 16 이상 다른 픽셀이 있는 파츠가 9개였고 `test_current/parts/bake/quality_worst.png`·`.json`에 있다. 차이는 투명 경계, 외곽선 안쪽 한두 픽셀, 그리고 binding 46140의 맨 윗줄(옆 파츠와의 이음매)이다. 이음매에 줄이 보이는지는 조립된 기체 화면에서 확인하지 않았다.

### 확인하지 못한 것

- 실제 플레이어(프로세스 3개)와 실제 게임 화면에서의 로딩.
- 검사 프로세스 속도가 37.6 → 31.6fps로 내려간 이유. 그릴 때 저장소에서 읽는 비용이거나 HD로 그려지는 양이 늘어서일 수 있다. 재지 않았다.
- 런타임 조립이 성공하는 파츠의 대기 시간. 이 파츠는 연결되기 전까지 집계에 잡히지 않는다.
- 조립 실패 기록으로 줄어든 시간.
- 롬을 새로 여는 조건의 시작 시간. 렌더 프로세스 초기화(목록 읽기 약 3초 + 구운 목록 대조 약 1초)는 그대로다.
- 배포판. 저장소를 사용자 캐시 폴더에서 찾으므로 구운 파일을 배포판에 넣는 방법을 정해야 한다.
