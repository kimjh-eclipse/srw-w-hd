# 화면 합성 재작성 계획 (교차 검토용)

작성: Claude, 2026-11-12. 코덱스의 검토를 요청한다. 9절의 질문에 답해 주면 된다. 이 문서는 계획이고, 1절에 "적용됨"이라고 적은 것 말고는 아직 구현하지 않았다.

## 1. 문제 정의

사용자 체감: 전투에 들어가기 전부터 화면이 느리다. PCSX2의 텍스처 교체는 빠른데 이 프로젝트는 느리다.

실제 플레이어에서 잰 값 (`test_current/performance/claude_trace/metrics.json`, `frame_trace.json`, 사용자 직접 플레이 약 110초):

| 경과 | 에뮬레이션 | 화면 표시 | 합성 1프레임 |
|---|---|---|---|
| 19~25초 | 60fps | 60fps | 3~5ms |
| 31~49초 | 60fps | 42~61fps | 6~14ms |
| 55~61초 | 60fps | 23~27fps | 28~35ms |
| 67~85초 | 60fps | 12~14fps | 39~69ms, 최악 114ms |

- 에뮬레이션은 항상 60fps다. 느린 것은 HD 합성이다.
- 60fps에는 프레임당 16.7ms가 한도다. 느린 구간은 그 3~4배다.
- 입력에서 화면 반영까지 257ms가 걸린 구간이 있다.
- 자동 해상도 조절은 이미 최저(768)까지 내려가 있었다.

**결론: 로딩 문제가 아니라 프레임당 합성 비용 문제다.** Claude가 앞서 한 사전 굽기(`docs/CLAUDE_REVIEW_RESULT.md` 7절)는 파츠가 처음 나올 때의 준비 시간만 줄였고, 이 문제에는 닿지 않았다.

## 2. 시간이 쓰이는 곳

### 2.1 실제 플레이어, 느린 구간 (emulated frame 3000~4500, 평균 61.8ms)

| 단계 | 프레임당 |
|---|---|
| 기체 파츠 합성 (`PartsRenderer.compose`, 위·아래 화면 합) | 20.2ms |
| 글자 인식 (`recognize`, 위 9.4 + 아래 2.6) | 12.0ms |
| 글자 그리기 (`compose`, 위 6.4 + 아래 4.0) | 10.4ms |
| GPU 그리기 + 읽어 오기 | 6.4ms |
| 맵·초상화·시나리오 배경 | 6.8ms |
| 그 밖 (프로세스 간 전달, 기록되지 않은 단계) | 약 6ms |

한 단계가 아니라 전 단계가 조금씩 무겁다. 어느 장면이었는지는 저장 상태가 없어 특정하지 못했다.

### 2.3 구조에서 오는 비용

지금의 한 프레임:

1. 에뮬레이션 프로세스가 화면 상태(네이티브 화면, 레이어 번호 지도, 소유자 지도, 파츠 표, 팔레트, OAM, BG 파츠 3200행 등)를 복사해 큐로 합성 프로세스에 보낸다.
2. 합성 프로세스가 파츠마다:
   - `sprite()`: PIL로 크기 조정·팔레트 재색칠·회전/반전·밝기 (결과는 캐시됨)
   - `PartVisibility.mask()`: 가림 마스크 계산 (DLL)
   - `Image.transform()`: 마스크를 파츠 크기로 변환 (PIL, **매 프레임, 캐시 없음**)
   - `eligibility()`, `gpu_plane()`: 전경 효과 판정 (numpy, **매 프레임**)
   - 마스크와 그림을 GPU 텍스처로 올림 (`id(image)` 기준 캐시라 마스크는 매번 새로 올라감)
3. GPU가 그린다. 파츠마다 그리기 호출 1회, 유니폼 10여 개 설정.
4. 완성 화면을 GPU에서 읽어 와 공유 메모리에 쓴다.
5. 표시 프로세스가 공유 메모리에서 읽어 다시 GPU에 올려 창에 그린다.

PCSX2는 텍스처를 한 번 GPU에 올린 뒤로는 원래 렌더러가 그리던 대로 그린다. 여기서는 2·4·5번이 매 프레임 CPU에서 일어난다.

### 2.4 Claude가 만든 비용 (적용됨, 수정 완료)

사전 굽기 이후 "준비된 파츠 목록"이 수백 개에서 약 9만 개로 커졌는데, 목록이 바뀔 때마다 파이썬 리스트로 만들어 프로세스 경계를 넘기고 C 배열로 변환하고 있었다. 2.2의 프로파일에서 `set_ready_parts`가 프레임당 6.4ms였다. numpy 배열로 바꿨다(`hd_parts.ready_bindings`, `hd_core.set_ready_parts`). 수정 후 수치는 아직 다시 재지 않았다.

## 3. 원칙

**CPU는 "무엇을 어디에 어떤 속성으로 그릴지"의 목록만 만든다. 픽셀을 만지는 일은 GPU가 한다.**

- 프레임당 CPU 작업은 그릴 항목 수에 비례하는 작은 표 작성으로 한정한다. 픽셀 수에 비례하는 CPU 작업(PIL 변환, numpy 화면 전체 연산)을 프레임 루프에서 없앤다.
- 텍스처는 처음 쓸 때 한 번 올리고 재사용한다.
- 화면 내용이 바뀌지 않은 것은 다시 계산하지 않는다(글자 인식, 배경 식별).
- 합성한 프로세스가 직접 화면에 표시한다.

## 4. 새 구조

### 4.1 GPU 파츠 합성기 (신규 `emulator/gpu_parts.py`)

`PartsRenderer.compose`를 대체한다. 그리는 순서와 판정 규칙은 지금과 같게 유지한다.

**텍스처**

- 구운 4배 RGBA(`parts_baked.sqlite`)를 파츠별 GPU 텍스처로 올린다. 선형 필터 + 밉맵. CPU 크기 조정이 없어진다.
- 팔레트 재색칠이 필요한 파츠는 지금의 CPU 재색칠 결과를 (binding, 팔레트) 단위로 한 번 만들어 별도 텍스처로 올린다. 재색칠 규칙(`material_map`, 잉크·붕괴·큰 변화 처리)은 건드리지 않는다. 팔레트가 프레임마다 바뀌는 효과가 있으면 이 방식은 프레임마다 올리게 되므로 9절 질문 2에 해당한다.

**프레임 입력 (작은 텍스처 4장, 256×192)**

- 레이어 번호 지도 (R8)
- 소유자 지도 (R8)
- 전경 효과 지도 (지금의 uint64를 RGBA16UI 등으로 풀어서)
- OBJ 우선순위 표 (128×1), BG 우선순위는 유니폼

**셰이더로 옮기는 판정**

- `native_composition.PartVisibility.mask` + `blend_mask`: 파츠가 어느 픽셀에서 보이는지, 앞쪽 BG의 알파가 걸리는지
- `foreground_blend.eligibility` + `blend_part`/`gpu_plane`: 앞쪽 BG의 색이 파츠에 섞이는 조건과 계수
- OBJ 반투명(모드 1), 밝기 올림/내림, 반전, 아핀

판정은 네이티브 픽셀 단위(256×192 격자의 nearest 조회)로 하고, 그림 샘플링만 고해상도로 한다. 지금 `Image.transform(..., NEAREST)`로 마스크를 키우는 것과 같은 결과가 나오도록 좌표 규칙을 맞춘다.

**프레임당 CPU 작업**

- `core.parts`(128행)와 `core.bgparts`에서 그릴 항목 표를 만든다: 텍스처, 위치, 아핀 행렬, 우선순위, 종류, 항목 번호, 제어값, 블렌드 계수.
- 우선순위 순으로 정렬해 그리기 호출을 낸다. 컷인 평면은 지금처럼 같은 순서 큐에 끼운다.

**유지하는 것**

- 코어가 숨긴 파츠는 반드시 그린다(bit31 규칙, `rescue`).
- 기체 단위 원본 유지(10% 규칙)는 코어에 있으므로 그대로다.
- `last_stats` 계수. 재생 검사가 계속 동작해야 한다.

### 4.2 직접 표시

합성 프로세스가 창의 GL 컨텍스트를 갖고 합성 결과를 바로 표시한다. GPU에서 읽어 오기, 공유 메모리, 표시 프로세스의 재업로드가 없어진다. 스크린샷(`capture`)만 읽어 오기를 쓴다.

Tk 창과의 결합 방식이 걸려 있다. 지금 `gpu_display.py`가 SDL 창을 쓰는 것으로 보이는데, 합성 컨텍스트를 그쪽으로 합치는 것이 가능한지 9절 질문 4.

### 4.3 글자

- 인식(`recognize`)을 프레임마다 4~5회 부르고 있다. 인식 대상 영역의 네이티브 픽셀 해시가 같으면 이전 결과를 쓴다.
- 그리기는 글리프를 아틀라스 텍스처로 올려 GPU 사각형으로 그린다.
- `clean_native`(네이티브 글자 지우기)도 영역 해시로 캐시한다.

### 4.4 나머지 레이어

- 컷인: `gpu_plane`의 numpy 연산을 4.1의 셰이더 경로로 합친다.
- 전투 배경: `identify`를 매 프레임 하지 않고 BG 레이아웃·맵 CRC가 바뀔 때만 한다.
- 시나리오 배경: `refresh` 안의 반복 `Image.open`을 없앤다.
- 초상화, 맵 타일, 아이콘, 라벨: 그림은 텍스처로 유지하고 프레임당 작업은 위치 표만.

## 6. 순서와 통과 조건

기존 코드는 지우지 않는다. 새 경로는 환경 변수로 전환할 수 있게 옆에 만든다. 단계마다 아래 조건을 통과해야 다음으로 간다.

| 단계 | 내용 | 통과 조건 |
|---|---|---|
| 0 | 기준선 고정 | 느린 장면의 저장 상태 확보. 기존 경로로 장면별 프레임 시간과 출력 그림 저장 |
| 1 | GPU 파츠 합성기 | 저장 상태 161개에서 기존 경로와의 픽셀 차이를 장면별로 기록. 차이가 큰 장면은 그림으로 확인. 재생 검사 FAIL 0. 파츠 합성 3ms 이하 |
| 2 | 직접 표시 | 실제 플레이어에서 표시 fps와 입력 지연 측정. 스크린샷 기능 유지 |
| 3 | 글자 | 글자 관련 기존 검사(`verify_fonts.py` 등) 통과. 인식 결과가 기존과 같음 |
| 4 | 나머지 레이어 | 장면별 픽셀 비교 |
| 5 | 실제 플레이 | 사용자 확인 |

픽셀 비교는 "같아야 통과"가 아니다. GPU 선형 필터와 PIL LANCZOS는 결과가 다르므로 차이는 반드시 생긴다. 차이의 크기와 위치를 기록하고, 가림 경계·이음매·반투명 영역은 그림으로 본다.

## 7. 위험

1. **판정 규칙의 이식 오류.** `PartVisibility`와 `eligibility`의 조건식을 GLSL로 옮기다 틀리면 레이어 순서가 장면에 따라 깨진다. 기존 경로와의 비교가 유일한 안전장치다. 기존 경로가 틀린 장면(사용자 제보의 대사창 침범, 효과 순서)은 비교로 잡히지 않고 틀린 채로 옮겨진다.
2. **그림 품질 차이.** LANCZOS 대신 밉맵 선형 필터를 쓰면 가는 선이 달라질 수 있다.
3. **GPU 메모리.** 한 전투에서 쓰는 파츠 텍스처 수와 크기를 재지 않았다. 4배 64×64 파츠는 256×256 RGBA = 262KB(밉맵 포함 약 350KB). 1,000개면 350MB.
4. **그리기 호출 수.** BG 파츠가 최대 3200행이다. 파츠마다 호출하면 호출 비용이 다시 병목이 될 수 있다. 그 경우 아틀라스 + 인스턴싱이 필요하다.
5. **GL 드라이버 차이.** 지금 셰이더는 GLSL 330이다. 정수 텍스처와 `texelFetch`를 쓰므로 330으로 충분하지만, 사용자 기기(ONE XPLAYER 내장 GPU) 말고는 시험하지 못한다.
6. **범위.** 1~4단계는 합성 모듈 대부분을 다시 쓰는 일이다. 중간에 멈추면 두 경로가 공존하는 상태가 남는다.

## 8. 하지 않는 것

- 그림이 없는 파츠(650종), BG 그림, 틀린 그림 연결. `docs/IMAGE_REWORK_FOR_CODEX.md`의 일이다. 이 재작성으로 좋아지지 않는다.
- 코어의 2D 렌더러를 고해상도로 바꾸는 것. 원리상 가장 깔끔하지만 DeSmuME의 스캔라인 렌더러를 다시 쓰는 일이라 이번 범위에서 뺐다. 9절 질문 1.
- 대사창 침범, 보조창 그림 오류 등 기존 결함의 수정. 재작성 중에 원인이 보이면 따로 기록한다.

## 9. 코덱스에게 묻는 것

1. **구조 선택.** 4절은 "파이썬이 목록을 만들고 moderngl 셰이더가 그린다"이다. 대안은 합성 전체를 코어 DLL 안의 C++로 옮기는 것이다. 지금 구조를 만든 입장에서, 파이썬 쪽에 남겨야만 하는 이유가 있는 단계가 있는가? 반대로 C++로 가야 하는 이유가 있는가?
2. **팔레트가 프레임마다 바뀌는 파츠.** 섬광·페이드처럼 팔레트가 연속으로 바뀌는 경우가 실제로 얼마나 있는가? 많다면 재색칠을 셰이더로 옮겨야 한다(인덱스 맵 + 잔차 텍스처). `material_map`의 잉크·붕괴·큰 변화 분기 중 셰이더로 옮길 수 없는 것이 있는가?
3. **느린 장면.** 2.1의 구간(부팅 후 약 50~75초, 전투 전, 파츠 합성 20ms)은 어떤 화면으로 보이는가? 맵에서 유닛 아이콘이 많은 화면인가, 인터미션 메뉴인가? 재현할 저장 상태가 있으면 경로를 알려 달라.
4. **표시 경로.** `gpu_display.py`·`frame_process.py`·`player_worker.py`의 3프로세스 구조에서 합성과 표시를 한 프로세스로 합치는 데 걸리는 제약이 있는가? 오디오가 합성 프로세스의 GIL을 기다리지 않게 하려고 나눈 것으로 읽었는데 다른 이유가 있는가?
5. **기존 경로가 틀린 것으로 알려진 장면.** 비교 기준에서 빼야 하는 장면 목록이 있는가?
6. **`PartVisibility`와 `eligibility`의 의도.** 조건식에서 실기 동작이 아니라 특정 장면을 맞추려고 넣은 예외가 있으면 표시해 달라. 셰이더로 옮길 때 그대로 옮길지 정리할지 판단해야 한다.

## 11. 검토 반영 (2026-11-12)

### 코덱스 검토

1. 합성을 GPU로 옮기는 방향은 타당하다.
2. 에뮬레이션은 별도 프로세스로 유지하고, **합성과 표시를 같은 GPU 컨텍스트로 통합하는 것을 먼저** 한다. 지금 합성은 숨은 OpenGL 컨텍스트(moderngl standalone), 표시는 SDL 렌더러(`gpu_display.py`)라서 프로세스만 합쳐서는 읽어 오기가 없어지지 않는다.
3. 이미 깨진 장면을 검사에서 빼지 않는다. "기존 결과와 같은가"와 "올바른 그림인가"를 따로 판정한다.

### 그에 따른 변경

- 순서: **직접 표시(4.2)를 1단계로 올리고**, GPU 파츠 합성기(4.1)를 2단계로 내린다. 직접 표시가 먼저 있어야 이후 레이어를 읽어 오기 없이 GPU에 남겨 둘 수 있다.
- 4.2의 방식: 합성 프로세스가 UI 캔버스의 자식 창(WS_CHILD, WS_DISABLED)을 만들고 그 창의 WGL 컨텍스트에서 합성과 표시를 모두 한다. 3프로세스 구조는 유지한다(UI / 에뮬레이션 / 합성+표시). 창 배치(위·아래 화면 사각형)는 UI가 합성 프로세스에 전달한다. 스크린샷만 읽어 오기를 쓴다.
- 6절의 통과 조건을 둘로 나눈다.
  - **동일성**: 새 경로와 기존 경로의 픽셀 차이. 전 장면 대상, 제외 없음.
  - **정확성**: 그림이 올바른가. 기존 경로가 틀린 장면은 동일성을 통과해도 정확성 실패로 남긴다. 사용자 제보 장면(대사창 침범, 효과 순서, 보조창 그림, 파츠 깨짐)을 정확성 목록의 초기 항목으로 둔다. 정확성 판정은 사람이 그림을 보고 한다.
- 9절 질문 5("비교 기준에서 뺄 장면")는 철회한다.

### 사용자와 정한 것

- 파츠마다 그리기 호출을 내지 않는다. 항목 표를 한 번에 넘겨 인스턴싱으로 그린다. BG 파츠가 최대 3,200행이라 파이썬에서 항목별 호출을 하면 호출 비용만으로 한도를 넘는다. 7절 위험 4는 위험이 아니라 설계 전제다.

  - 새 표시 방식이 실패하는 기기에서는 기존 방식으로 자동 전환한다.

## 12. 코덱스 2차 검토 반영과 1차 구현 결과 (2026-11-12)

검토 문서: `docs/RENDER_REWRITE_REVIEW_CODEX.md`. 아래와 같이 받아들인다.

### 받아들인 것

- 2절의 단계별 시간은 포괄 시간이라 서로 겹친다(`FontRenderer.compose`가 `recognize`를 부르는 식). 합산하거나 전체에서 빼서 "나머지"를 구한 것은 잘못이다. 2.1의 "글자 약 22ms", "그 밖 약 6ms", "프로세스 간 전달" 표현은 근거가 없다. 배타 시간으로 다시 재기 전까지 세부 예산으로 쓰지 않는다. 61.8ms라는 전체 평균과 파츠 20.2ms는 코덱스가 같은 값으로 재확인했다.
- 그 기록은 합성 프로세스 안의 시간이다. 스냅샷 복사, 큐 대기, 표시 쪽 업로드는 들어 있지 않다.
- 진행 순서를 코덱스 권장대로 바꾼다: 0 느린 장면 확보와 배타 계측 → 1 글자 인식 공유·배경 refresh 캐시 → 2 동일 GL 컨텍스트 표시 → 3 GPU 파츠/전경 → 4 팔레트·글리프·나머지 → 5 EXE 실제 플레이.
- 인스턴싱을 전제로 못 박지 않는다. 명령 수와 제출 시간을 먼저 재고, 그리는 순서를 지키는 인접 묶기부터 한다. 11절의 "설계 전제" 표현은 철회한다.
- 가림 규칙을 셋으로 나눠 명세한다: 실기 우선순위를 표현하는 공통 규칙 / HD 미술 정책(`cutin_visibility`의 윤곽 밖 허용) / 대사창 좌표 휴리스틱(`draw_cutin`의 `ty>=120`, `render_top`의 cyan 감지). `eligibility`의 `behind` 허용은 실기 조건이 아니라 원본을 숨긴 뒤의 보상 규칙이다. 두 함수만 GLSL로 옮긴다고 정책 전체가 옮겨지지 않는다.
- 팔레트가 프레임마다 바뀌는 빈도와 느린 구간의 화면은 **미확인**으로 둔다.
- 텍스트 캐시 키, 배경 무효화 조건, 명령 버퍼 형식, 알파·밉맵 정책, GPU 캐시의 바이트 예산, p50/p95/p99 보고, headless와 실제 표시의 검증 분리(코덱스 8절 5~13항)는 해당 단계 설계에 넣는다.
- 알려진 결함 표(코덱스 질문 5)를 정확성 목록의 초기 항목으로 쓴다.

### 순서와 다르게 먼저 한 것

2단계(동일 GL 컨텍스트 표시)를 0·1단계보다 먼저 구현했다. 코덱스 검토가 도착하기 전에 가능성 시험을 마치고 연결 중이었기 때문이다.

- `emulator/direct_present.py` 신규: UI 캔버스의 자식 창(WS_CHILD, WS_DISABLED)과 WGL 컨텍스트. 창 크기는 합성 프로세스가 직접 읽는다(UI와 DPI 배율이 다를 수 있음).
- `gpu_surface.py`: `attach_window()`, `Backend.present()`. 합성 결과를 텍스처 FBO에 그리고 화면에 바로 그린 뒤 swap. 읽어 오기 없음. 아래 화면은 바뀔 때만 다시 그린다.
- `frame_process.py`·`frame_compositor.py`·`player_worker.py`·`hd_emulator.py`·`gpu_display.py`: 캔버스 HWND와 배치를 합성 프로세스에 전달, 직접 표시 프레임은 공유 메모리를 쓰지 않음.
- 환경 변수 `SRWW_DIRECT_PRESENT=0`이면 기존 경로. 자식 창이나 컨텍스트 생성에 실패하면 자동으로 기존 경로를 쓴다(`gpu_compositor_status.json`의 `direct_present_error`).
- 프로세스 구조는 그대로다(UI / 에뮬레이션 / 합성+표시).

- **작업 드라이브(D:)의 I/O 오류.** D:는 USB 외장 SSD(Realtek RTL9210)이고, 시스템 로그에 disk 이벤트 153(I/O 재시도)이 22:28에 1건, 22:49~22:52에 46건 있다. 같은 시각에 플레이어가 응답 없음이 됐고, 벤치마크에서 SQLite 읽기 한 번이 16초 걸렸다. 그릴 때 저장소에서 읽는 구조는 디스크가 멈추면 화면도 멈춘다.
- 22:42~22:54에 다른 쪽에서 `bake_parts.py --workers 4`가 돌았다(86,199개 재굽기, 저장소 1.27GB → 2.57GB). 그 사이의 측정과 그 전 기준 화면과의 비교는 버렸다. 이전 키의 행이 저장소에 남아 있다.
