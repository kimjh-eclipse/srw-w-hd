# 화면 합성 재작성 계획: 코덱스 교차 검토

작성일: 2026-11-12. 검토 대상: `docs/RENDER_REWRITE_PLAN.md` 9절의 질문 1~8.

이 문서는 코드와 기존 계측 자료를 읽고 작성한 검토다. 새 렌더러를 구현하거나 새 성능 시험을 수행한 결과가 아니다. 아래의 권장은 추정 성능을 달성했다고 의미하지 않는다.

## 결론

**파이썬은 그리기 목록을 준비하고 GPU가 픽셀을 처리하는 구조에 찬성한다.** 지금 단계에서 합성 전체를 DeSmuME 코어 DLL로 옮기는 것보다, 기존 코어 브리지를 유지하고 별도 GPU 합성 경로를 만드는 편이 변경 범위와 비교 검증에 유리하다.

단, 우선순위를 수정할 것을 권한다. 느린 장면 재현과 계측 구간 중복 제거가 먼저다. 다음은 글자·배경의 중복 계산을 줄이는 독립 개선과, 합성/표시가 동일 GPU 컨텍스트를 사용하는 작은 시제품이다. 그 뒤 가림·팔레트·변형을 순차적으로 셰이더에 옮긴다. 전체 파츠 경로를 먼저 완성하고 나중에 표시 구조를 바꾸면 컨텍스트·텍스처 수명 관리 코드를 두 번 만들 수 있다.

그림 누락·틀린 그림·파츠 이음매는 별도 자산 작업이다. 렌더러를 바꿔도 자동으로 해결되지 않는다.

## 근거와 계측 해석상의 정정

확인한 파일:

- `emulator/frame_trace.py`, `frame_compositor.py`, `frame_process.py`, `player_worker.py`
- `emulator/hd_parts.py`, `hd_renderer.py`, `native_composition.py`, `foreground_blend.py`, `painted_edges.py`
- `emulator/gpu_surface.py`, `gpu_display.py`, `hd_fonts.py`, `palette_materials.py`
- `test_current/performance/claude_trace/frame_trace.json`, `metrics.json`

프레임 기록은 4,727행이며, emulated frame 3000~4500에 속하는 합성 기록 368행을 다시 집계했다. 합성 전체 평균은 **61.7815ms**로 계획의 값과 일치한다. `parts` 평균은 20.189ms, `gpu_draw_read`는 6.387ms다. GPU 읽기 비용이 존재하지만 이것 하나만 제거해 60fps가 된다는 설명은 맞지 않는다.

**단계별 시간은 서로 독립적이지 않다.** `FrameTrace.wrap()`은 함수 진입부터 복귀까지의 포괄 시간을 기록한다. 예를 들어 `FontRenderer.compose()`가 `recognize()`를 부르므로 `font_paint`와 `font_scan`은 일부 중복된다. `bottom_font`/`bottom_font_scan`, `glyph`/`font_paint`, `top`/하위 단계도 마찬가지다. 따라서 표의 모든 단계를 더하거나 이를 전체에서 빼서 미계측 시간을 계산하면 안 된다. 글자 비용 약 22ms와 나머지 약 6ms는 배타 시간으로 다시 산출해야 한다.

또한 이 trace의 `finish()`는 합성 작업 프로세스 안에서 호출된다. 에뮬레이션 측 snapshot 복사, 큐 직렬화와 대기, 표시 측 업로드·present 전체를 포함하는 종단 시간계가 아니다. **기록되지 않은 시간을 곧바로 프로세스 간 전달 비용으로 단정할 수 없다.** 이것은 합성 병목이라는 결론을 뒤집는 것이 아니라 세부 예산을 바로잡는 일이다.

GPU 계측 범위도 보완해야 한다. 현재 `frame_trace.py`는 `Backend.render()`를 감싸지만, `render_pair()`는 별도 읽기 채널의 `read()` 안에서 `render(..., draw_only=True)`를 콜백으로 부른다. 이 경로에서는 콜백 밖의 읽기/대기가 `gpu_draw_read`에 모두 잡힌다고 보장할 수 없다. 일반 render와 paired/persistent readback의 종단 시간을 각각 계측하고 포괄 시간 중복을 제거해야 한다.

## 질문 1. 파이썬+셰이더인가, 코어 C++ 이식인가?

**답: 우선 파이썬+셰이더. 파이썬에 반드시 남아야 하는 렌더 단계는 없다.** 다만 현재 라이브러리 해석, 에셋 관리, 글꼴 인식, UI·설정이 파이썬에 있어 전부 C++로 옮기는 비용이 크다.

지금의 핵심 낭비는 언어 자체보다 픽셀 배열의 반복 생성·변환·업로드·읽기다. PIL 작업을 동일하게 C++ CPU 코드로 옮겨도 GPU 왕복과 반복 가공은 남는다. 반대로 파이썬이 소량의 명령 버퍼만 만들고 픽셀 연산을 셰이더로 넘기면 해당 낭비를 직접 제거할 수 있다.

권장 경계:

| 위치 | 책임 |
|---|---|
| DeSmuME 코어 | 에뮬레이션, native 가림/소유자/블렌드 정보, 원본 숨김 결정 |
| 파이썬 | 자산 조회, 명령 버퍼 작성, 준비 상태·자산 세대 관리, UI |
| GPU | 샘플링, 변형, 가림, 색·반투명·밝기, 레이어 합성, 화면 표시 |
| 사전 제작 도구 | 정렬, 가장자리 처리, 재질 인덱스/잔차 생성, 텍스처 굽기 |

명령 제출이 다음 병목으로 측정되면 그 버퍼 작성/제출 부분만 네이티브 확장으로 옮긴다. 코어로 옮겨야 할 정당한 이유는 고해상도 스캔라인 재구성처럼 **현재 브리지가 내보내지 않는 실기 정보를 합성에 써야 하는 경우**다. 이 경우도 먼저 브리지 보강과 별도 합성기를 비교해야 한다. C++ 전체 이식이 성능 또는 정확성을 자동 보장하지 않는다.

## 질문 2. 연속 팔레트 변화와 재색칠 셰이더 이식

**발생 빈도는 아직 모른다.** 기존 자료에서 활성 파츠별 팔레트 변화를 집계한 근거는 찾지 못했다. 임의로 적다/많다 또는 몇 %라고 답하지 않는다.

`PartsRenderer.sprite()`는 동적 파츠의 캐시 키에 `row[4]`를 넣고, 실제 팔레트가 다르면 `material_map()`과 NumPy 색 변환을 수행한다. 연속 변화가 있으면 새 변형 텍스처가 반복 생성되고 캐시를 밀어낼 수 있다. 현재 파츠 그림 캐시 수 제한도 함께 확인해야 한다.

측정 추가안:

- 활성 binding별 인접 프레임의 팔레트 해시 변경 횟수 및 전체 고유 팔레트 수.
- 같은 binding·같은 팔레트의 캐시 적중률, 새 재색칠 CPU 시간·업로드 바이트.
- 단순 밝기/색조 변화와 완전히 다른 재질 팔레트 전환을 구분.
- `row[4]` 변경만 보지 말고 실제 사용된 16색 값도 확인. 기록은 매 프레임 파일 쓰기 대신 메모리에 모아 종료 시 저장.

**현재 분기 중 원리적으로 셰이더로 옮길 수 없는 것은 없다.** 그러나 매 픽셀마다 가장 가까운 색을 검색하는 방식 그대로 옮기지 않는다.

1. 그림과 기준 재질 인덱스 맵, 잔차를 사전 생성한다. 인덱스 맵은 nearest로 읽는다.
2. 사용 인덱스 집합, 잉크 보호 등 고정 정보도 굽는다.
3. 팔레트 변경 시 16색 및 재질별 명암 계수, 동일 색 붕괴 마스크, 큰 색 변화 여부만 계산해 작은 버퍼/텍스처로 전달한다.
4. 셰이더에서 목표 색과 잔차를 합성한다. 알파는 별도로 유지한다.

`material_map()`의 엄격한 native 재질 경계, 잉크 보호 및 `palette_materials.material_indices(strict=True)`는 기존 출력의 픽셀 얼룩을 재현할 수도 있다. **수학적으로 이식 가능하다는 것과 미술적으로 올바르다는 것은 다르다.** 데스사이즈의 손상된 그림처럼 원본 HD 자체의 문제도 있으므로, 재질 규칙 변경과 그림 교체를 같은 비교에 섞지 않는다. 잔차의 정밀도/부호, 반투명 경계의 색 공간도 명시해야 한다.

## 질문 3. 느린 구간은 어떤 화면인가? 저장 상태가 있는가?

**현재 자료만으로 특정할 수 없다. 해당 50~75초 구간에 대응한다고 확인한 저장 상태도 없다.** 파츠 비용이 크다는 이유만으로 유닛 많은 지도나 인터미션이라고 단정하면 안 된다. `parts`는 위·아래 화면에서 모두 호출되고, 아래 화면의 유닛 그림도 포함한다. emulated frame 번호와 실제 경과 시간도 일대일 장면 식별자가 아니다.

다른 전투 저장 상태는 많지만 해당 느린 구간의 대체 증거로 쓰지 않는다. 단기적으로 실제 플레이어에 다음 묶음을 **같은 프레임 번호로** 저장하는 진단 기능을 권한다:

- ROM 해시, 빌드/렌더 경로, 코어 프레임 번호, 해상도, 레이아웃, HD 설정.
- native 두 화면과 최종 표시 화면, 활성 OBJ/BG 파츠 및 컷인 ID·팔레트·배경 식별자.
- 같은 코어 프레임의 저장 상태와 입력 시각/표시 시각.
- 자산·구운 저장소 식별자와 캐시의 cold/warm 상태.

합성 시간이 임계값을 넘으면 코어는 이미 더 진행했을 수 있다. **그때 저장한 최신 코어 상태를 느린 합성 프레임의 상태라고 적으면 안 된다.** 소량의 주기적 상태와 입력 기록을 연결하거나, 재현 모드에서 프레임 경계를 동기화해 정확한 대응 상태를 확보해야 한다. 먼저 수동 저장과 화면/프레임 표식을 붙이는 작은 구현부터 가능하다.

## 질문 4. 합성·표시 통합의 제약과 프로세스 분리 이유

현재 코드의 이유는 오디오/GIL 격리만이 아니다.

- `player_worker.py`: ROM/세션을 새 프로세스에서 시작해 코어 이중 초기화를 피하고 코어 크래시가 UI를 종료하지 않게 한다.
- `frame_process.py`: HD 합성의 파이썬 GIL이 native 오디오/에뮬레이션을 지연시키지 않도록 한다.
- `frame_compositor.py`: 불변 snapshot을 전달하고 대기 큐를 1개로 제한한다. 렌더 지연으로 오래된 화면이 계속 쌓이지 않게 한다.
- 별도 텍스처 준비·패드 프로세스도 존재하므로 실제 프로세스가 항상 정확히 3개인 것은 아니다.

**에뮬레이션/오디오는 별도 유지하고, 합성과 표시를 같은 프로세스·같은 GPU 컨텍스트로 합치는 것을 권한다.** 패드/준비 작업은 독립 판단한다.

중요한 실제 제약:

1. `gpu_display.py`는 Tk의 HWND를 `pygame._sdl2.video.Window.from_window()`로 감싸 **SDL Renderer**에 그린다. 이것은 합성용 ModernGL 컨텍스트가 아니다.
2. `gpu_surface.Backend`는 별도의 `moderngl.create_standalone_context(require=330)`를 만든다. 두 경로를 같은 프로세스에 놓는 것만으로 텍스처를 공유하거나 읽기/재업로드를 제거할 수 없다.
3. 표시 창에 연결된 GL 컨텍스트를 만들고 합성기도 그 컨텍스트를 주입받도록 해야 한다. Tk 메인 스레드·SDL 이벤트·창 크기 변경·전체화면·컨텍스트 현재 스레드 규칙을 함께 설계해야 한다. 외부 HWND에 단순 OpenGL 플래그를 추가하면 된다고 가정하지 않는다.
4. GPU 호출은 컨텍스트를 소유한 스레드에서 한다. UI를 막는 긴 CPU 작업과 SQLite 읽기는 별도 준비 경로에 둔다.
5. UI/표시 합성 통합 시 합성 예외가 창을 닫을 수 있다. 에뮬레이션 프로세스 격리는 유지하고 장치 재생성·기존 경로 복귀를 준비한다.

코어→합성 snapshot 전송은 이 변경 이후에도 남는다. 제거되는 것은 완성 HD 화면의 GPU 읽기→공유 메모리→표시 GPU 업로드 구간이다. 캡처·자동 비교에서는 읽기를 계속 허용한다.

## 질문 5. 기존 경로가 틀린 장면과 비교 기준

**검사에서 빼지 말고, 기존 출력이 정답인 비교에서만 제외한다.** 두 검사를 병행한다:

- 회귀 비교: 새 경로가 기존 경로와 예상 밖으로 달라진 곳을 찾는다.
- 정확성 비교: native HD OFF 출력, 고정된 기대 레이어/소유자/색 및 사용자 제보로 옳고 그름을 판단한다.

| 알려진 결함 | 자료/장면 | 기존 출력을 정답으로 삼을 수 없는 부분 |
|---|---|---|
| 대사창 침범 | `unit_155/mechanical_cutin_130.state`, 겟타/고라이온 컷인 상태 | 이름칸·대사 프레임과 HD 객체 겹침 |

위 저장 상태 경로는 `test_current/combat/` 기준이며 named 장면은 `named_attacks/` 아래다. 제보마다 기대 순서와 정상 참고 그림을 붙인 결함 목록을 따로 관리해야 한다. 여기 적힌 상태를 모두 정상으로 확인했다는 의미는 아니다.

## 질문 6. 가림 조건의 의도와 예외

`PartVisibility`의 기본 목적은 native 픽셀의 최종 레이어/OBJ 소유자와 우선순위에서 HD 객체가 보일 곳을 정하는 것이다. BG 동률은 작은 레이어 번호 우선, OBJ/BG 동률과 OBJ 번호 순서도 반영한다. `eligibility()`는 앞쪽 BG가 첫 알파 대상이고 HD 객체가 두 번째 대상일 때 RGB를 섞는 후보를 고른다.

다만 이것은 전체 하드웨어 렌더러를 그대로 재현하는 코드가 아니다. 다음을 구분해야 한다:

| 위치/규칙 | 성격과 주의점 |
|---|---|
| `PartVisibility.mask()`의 BG/OBJ 우선순위와 owners 비교 | 실기 우선순위를 표현하려는 공통 규칙. 동률을 별도 테스트할 것 |
| `blend_mask()`의 BLDCNT 비트/EVA·EVB 처리 | 공통 알파 의도. foreground 경로와 중복 감쇠되는지 테스트 필요 |
| `eligibility()`의 실제 대상 일치/배경색 허용 | 첫/두 번째 알파 대상의 인접성을 표현하려는 규칙 |
| `eligibility()`의 `behind` 허용 | **원본 HD OBJ를 숨긴 뒤 더 뒤의 BG가 native 대상처럼 기록되는 상황을 보상하는 프로젝트 규칙.** 실기 조건식 자체라고 설명하면 안 됨 |
| `painted_edges.cutin_visibility()`가 native 윤곽 밖 HD를 허용 | HD의 매끈한 외곽을 원본 계단 마스크로 자르지 않으려는 미술 정책 |
| `hd_renderer.draw_cutin()`의 `last_matches`, `ty >= 120` 주변을 visible=255로 강제 | **대사 글자 칸이 컷인에 구멍을 내던 문제를 피하기 위한 화면 좌표 휴리스틱.** 실기 레이어 규칙이 아님 |
| `render_top()`의 cyan 감지 후 y=128..191 native UI 재삽입 | **전투 대사창용 휴리스틱.** 다른 배치·투명 UI·컷인 전환에서 검증 부족 |
| 불투명 256×256 평면 반복 | 실제 BG 반복을 복원하려는 등록별 처리. 그림 크기만 보고 다른 레이어까지 반복시키면 안 됨 |

순수 `PartVisibility`/`eligibility` 안에서 특정 기체 ID를 직접 분기하는 코드는 확인하지 못했다. 하지만 위의 대사창 좌표 예외와 등록별 metadata가 호출자에 있으므로 **두 함수만 GLSL로 옮긴다고 전체 정책이 옮겨지는 것은 아니다.**

추가 한계: 최종 레이어 지도는 모든 중간 레이어와 창 판정을 완전히 담지 못한다. BG 우선순위·제어값이 scanline 중간에 바뀌는 장면에서 전역 값만 사용하면 정보가 부족할 수 있다. 코어의 window/알파/raster 처리와 전달 필드의 수명을 대조해야 한다. 새 경로도 입력에 없는 정보를 셰이더만으로 복원할 수 없다.

권장: 공통 native 규칙과 HD 미술 정책, 대사 UI 예외를 별도 명세로 분리한다. 기존 예외는 우선 호환 모드로 유지하되 정확성 기준 없이 몰래 제거하거나 새 셰이더에 영구 고정하지 않는다. window·동률·다중 반투명·가림 객체·변형·부분 화면 밖·마스터 밝기를 각기 검사한다.

## 질문 7. 측정에서 빠질 수 있는 비용

아래는 **현재 병목으로 측정됐다는 뜻이 아니라 코드에 존재해 분리 측정할 항목**이다.

| 항목 | 확인 위치/측정 방법 |
|---|---|
| snapshot 복사·unknown snapshot 생성·큐 pickle | `FrameCompositor.snapshot/submit`; 바이트/시간/큐 체류/거절 수 |
| 준비 목록·동적 바인딩 전달 | `ready_bindings`, `set_ready_parts`; NumPy 변경 후 실제 재측정 |
| native 브리지 복사·에셋 테이블 갱신 | 코어 실행과 분리해 타이밍 |
| 구운 DB 읽기·WebP 해독·rescue | cold/warm·적중/실패·강제 동기 준비별 |
| GPU 텍스처 생성·퇴출·재업로드 | `Backend.texture`; 현재 192개 제한. 파츠/마스크가 서로 밀어내는지 확인 |
| 프레임버퍼·좌표 맵·셰이더 설정·드로콜 | 명령 수와 CPU 제출/GPU 실행 시간을 각각 기록 |
| GPU 완료 대기·읽기 동기화 | `render` 벽시계는 앞선 드로콜의 대기를 포함할 수 있음. GPU 타이머는 지연 조회 |
| 공유 메모리 lock 및 표시 업로드/present | `frame_process`, `GPUDisplay.draw`; 종단 화면 프레임 ID 연결 |
| 원본 글자 복구·마스크 변환·배경 파일 열기 | 함수별 배타 시간과 호출 수/적중률 |
| 초기 글꼴 준비·런타임 조립·GC | 첫 진입과 정상 유지 프레임을 별도 집계 |

GLSL만 빨라져도 텍스처 캐시가 계속 퇴출되면 효과가 줄어든다. 개수만의 제한 대신 GPU 메모리 바이트 예산과 최근 사용을 기준으로 하고, 현재 프레임의 모든 그리기 자원은 제출 완료 전 퇴출하지 않게 해야 한다. 89,199개 전부를 GPU에 올리는 방식은 권하지 않는다.

## 질문 8. 계획의 수정·추가 사항

### 동의하는 항목

- 프레임당 PIL/화면 전체 NumPy 연산을 줄이고 정수 native 지도와 GPU 샘플링으로 전환.
- 기존 경로 보존과 선택 가능성, 단계별 측정, 그림 누락과 성능 작업 구분.
- 최종 표시 60fps, 합성 12ms, 입력 지연 50ms를 **목표로만** 명시한 점.

### 수정할 항목

1. **시간표를 배타 시간으로 다시 작성.** 포괄 시간 중복과 측정 범위 밖의 전달 비용을 분리한다. 61.8ms는 확인되지만 세부 합계는 그대로 예산으로 쓸 수 없다.
2. **느린 장면 확보를 단계 0의 필수 조건으로 유지.** 재현 없이 시제품은 만들 수 있지만 해당 느린 구간을 해결했다고 보고하지 않는다.
3. **컨텍스트 통합 시제품을 앞당김.** 화면 한 장을 동일 GL 컨텍스트로 합성→표시하고 창 조절/전체화면/입력을 먼저 확인. 에뮬레이션 격리는 유지.
4. **글자·배경 중복 호출 제거는 독립 소규모 변경으로 먼저 가능.** 같은 프레임 인식 결과 공유와 refresh의 반복 파일 열기 제거는 전체 재작성을 기다릴 이유가 없다. 단, 실제 캐시 적중률을 잰다.
5. **텍스트 캐시 키는 픽셀 해시 하나로 충분하지 않음.** 화면·영역·인식 설정·폰트/자산 세대·색/선택 상태를 포함한다. 영역 분할은 글자 경계와 움직이는 창을 고려하고, 지우기용 배경은 배경이 변하면 별도로 무효화한다.
6. **배경 식별은 레이아웃과 map CRC만으로 부족할 수 있음.** 타일 VRAM/팔레트 변경, affine·스크롤·raster 변화도 식별과 표시의 서로 다른 무효화 조건으로 나눈다. 화면 전체 CRC를 무작정 매번 계산하면 절약이 상쇄될 수 있다.
7. **처음부터 명령 버퍼 형식을 고정.** stable texture ID/세대, screen, native 좌표, source rect, transform, 우선순위/동률 키, 제어값, 팔레트 ID, frame ID를 포함. Python 객체 ID를 영구 자산 ID로 쓰지 않는다.
8. **순서를 보존하는 배칭.** 반투명 객체를 텍스처별로 무조건 재정렬하면 결과가 달라진다. 순서가 유지되는 인접 항목 묶기부터 시작한다. 인스턴싱이 처음부터 필수라는 근거는 아직 없다.
9. **정수 지도는 nearest/texelFetch, 보간은 그림에만.** 64비트 packed 값을 지원되는 정수 채널로 손실 없이 분해. EGL/WGL·드라이버별 업로드 형식과 바이트 순서를 명시한다.
10. **알파와 밉맵 정책 명세.** straight/premultiplied 알파를 섞지 말고 투명 경계의 RGB·패딩·밉맵 번짐을 시험한다. 선형 필터만으로 파츠 이음매가 해결되지 않는다.
11. **비동기 준비와 bit31 일관성 유지.** 숨겨진 텍스처가 없으면 조용히 건너뛰지 않는다. rescue 실패도 실패로 기록하며, core ready와 GPU resident를 혼동하지 않는다. GPU 캐시에서 퇴출된 자산의 재업로드 경로도 필요하다.
12. **단순 평균 대신 p50/p95/p99와 드롭·입력 지연 보고.** 12ms는 전체 프레임 16.7ms 중 일부 예산이며 present·입력·큐 대기가 남는다. 전시 FPS만이 아니라 새 프레임 표시율과 표시된 프레임의 나이도 기록한다.
13. **검증을 headless와 실제 표시로 분리.** 캡처 경로는 의도적으로 GPU 읽기를 수행하므로 직접 표시 성능 시험과 분리한다. paused/synchronous 준비를 정상 플레이 성능 근거로 쓰지 않는다.
14. **배포 경로도 포함.** 개발 PC의 구운 DB를 쓰는 성공과 배포 EXE의 성공은 별개. 새 경로·셰이더·텍스처 저장소·DLL을 실제 EXE에서 검증하고 ROM/세이브는 포함하지 않는다.

### 권장 진행 순서

| 순서 | 결과물 | 판정 |
|---|---|---|
| 0 | 느린 장면의 동기화된 상태·화면·프레임 기록, 배타 계측 | 재현 가능 여부부터 명시 |
| 1 | 같은 프레임 글자 인식 공유·배경 refresh 캐시 | 화면 차이와 적중률/시간 비교 |
| 2 | 동일 GL 컨텍스트 합성→표시 최소 시제품 | 실제 창·입력·전체화면·복귀 동작 |
| 3 | GPU 파츠/전경 합성 경로 | 정수 규칙 테스트 + 전체 상태 회귀 + 알려진 실패의 기대 결과 검사 |
| 4 | 팔레트/글리프/나머지 레이어 GPU화 | 단계별 비용을 보고 필요한 부분부터 |
| 5 | 최신 EXE의 실제 플레이 | cold/warm, p95/p99, FPS·입력 지연·시각 확인 |

어느 단계에서도 이미지 누락 650종이나 다른 기체 그림의 오연결이 해결됐다고 합산하지 않는다. 이 문서는 구조 검토까지이며, 성능 목표 달성·실제 게임 정상·배포 완료를 인증하지 않는다.
